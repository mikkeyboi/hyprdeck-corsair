# Corsair K100 family: protocol research for the hyprdeck keyboard plugin

Scope: K100 RGB (optical and mechanical) and K100 AIR Wireless, compared with the K65 PLUS Wireless (the user's main keyboard). This is a clean-room protocol description. OpenLinkHub (OLH, GPL-3.0) is used as a reference only: no OLH code is copied here, only facts about bytes, ids and ordering.

Paths are relative to `<scratch>/src/`:

- `OLH/` = `OpenLinkHub/`
- `CKB/` = `ckb-next/` (GPL-2.0)
- `ORGB/` = `OpenRGB/Controllers/CorsairPeripheralV2Controller/` (GPL-2.0)

Confidence tags:

- **[V]** VERIFIED-IN-SOURCE: one source shows it, cited by file:line.
- **[C]** CORROBORATED: two or more independent sources agree.
- **[I]** INFERRED: reasoned from patterns but not confirmed directly.

---

## 0. Executive summary

1. **Every K100 variant uses Bragi, the same protocol family as the K65 PLUS.** No K100 variant uses the legacy NXP/K70 protocol. ckb-next lists all three K100 RGB PIDs in `USES_BRAGI` and in `USES_BRAGI_JUMBO` (`CKB/src/daemon/usb.h:313,316`). OLH drives them with the same Bragi command set it uses for the K65 PLUS (`OLH/src/devices/k100/k100.go:126-153`). **[C]**
2. **The main difference is the frame size.** The K100 RGB and the K100 AIR wired both use **1024-byte "jumbo" Bragi frames** on the vendor interface. The K65 PLUS (wired and dongle) and the K100 AIR over its dongle use 64-byte frames.
   - OLH: `bufferSize = 1024` (`k100.go:157`, `k100airWU.go:155`) versus 64 (`k65plusWU.go:151`).
   - ckb-next: `BRAGI_JUMBO_SIZE 1024` (`CKB/src/daemon/structures.h:244`).
   - OpenRGB sends the K100 RGB 65-byte writes (64 plus report id, `ORGB/CorsairPeripheralV2Devices.cpp:1438-1440`) and it still works, so the device appears to accept short OUT transfers. **[C]** for 1024, **[I]** that 64 is also accepted.
   - The plugin should take the frame size from the HID report descriptor (sysfs), not hard-code it.
3. **The K100 RGB has one 193-LED lighting buffer**, LED ids 0..192, written on Bragi resource **0x22** with a `12 00` prefix followed by interleaved R,G,B bytes. The buffer covers:
   - keys at their key-bit index
   - G1..G6
   - the 44-zone LightEdge (top 22, left 11, right 11)
   - the 8-LED control-wheel ring
   - the 3-segment logo

   **[C]** by OLH, ckb-next and OpenRGB.
4. **Control wheel events arrive on hidraw interface 2.**
   - Rotation: `byte[1] = 0x05`, `byte[2] = 0x60`, `byte[4] = 0x01` for clockwise or `0xFF` for counter-clockwise (ckb-next reads `byte[4..7]` as a signed i32).
   - Wheel press: key bit 137 in the normal 0x02 key bitfield.

   **[C]**
5. **The K100 AIR has two PIDs.** Wired it is **1b1c:1bab**. Over SLIPSTREAM it pairs with the generic **1b1c:1ba6** receiver and appears as a sub-device (PID 0x1bab). Wired, it behaves like the K100 RGB (jumbo frames, resource 0x22, 137 LEDs). Through the dongle, OLH drives only firmware lighting effects stored as Bragi "files", the same approach as the K65 PLUS dongle. **[C]**
6. **Onboard profiles (8 MB, up to 200) are not implemented by any open-source project.** ckb-next disables hardware profile loading for all Bragi devices (`CKB/src/daemon/device_bragi.c:194`). The only public trace of the storage mechanism is the Bragi file-handle sequence OLH uses for wireless hardware lighting: open, write, close, then `0x15` commit, plus a `0x0b` command. **[I]**
7. **OPX switches have no adjustable actuation.** Adjustable actuation exists only on MGX/Hall-effect boards such as the K70 MAX (`OLH/src/devices/k70max/k70max.go:133,141` has `dataTypeKeyActuation`; the k100 package has nothing similar). iCUE offers a debounce setting on some K100 units. OLH implements debounce (1-9 ms) for the K100 only; a Corsair forum post (Dec 2024) says iCUE 5.22 does not show it on the OPX version. **[C]** for "no adjustable actuation", **[I]** for debounce on OPX.

### 1.1 HID interfaces (wired K100 RGB / K100 AIR)

- **IF0:** standard boot keyboard and NKRO. This is the keyboard the OS sees. **[I]** (same family layout as the K65 PLUS)
- **IF1:** vendor page **0xFF42**, the command channel. OLH opens interface 1 (`devices.go:847-850`, first tuple field = InterfaceId 1, with lookup at `devices.go:511-521`). OpenRGB detects `interface 1, usage page 0xFF42` (`ORGB/CorsairPeripheralV2ControllerDetect.cpp:108-110`). **[C]**
- **IF2:** vendor IN-only event channel (key bitfield and wheel). OLH opens `InterfaceNbr == 2` as the "listener" (`k100.go:3132`, `k100airWU.go:3100`). **[V]**
- **USB endpoints (libusb view):** ckb-next uses OUT EP **0x01** and IN EP **0x82** for the K100 (`CKB/src/daemon/usb_bragi.c:35-40`), not the default 0x04/0x84. This does not matter with hidraw. **[V]**
- **Event report length:** ckb-next only parses 0x02 key and 0x05 dial packets when `urblen == 64` (`CKB/src/daemon/keymap.c:908-925`). So events stay 64 bytes even on jumbo devices; only the command channel is 1024. **[V]**

## 2. Bragi framing (shared with the K65 PLUS, K100 specifics noted)

### 2.1 Request frame (hidraw write)

Layout: `[0]=0x00` (report id), `[1]=target`, `[2]=cmd`, `[3..]=args`. The frame is padded to the report size: 1024 for K100 wired, 64 for dongle and K65.

- **target:** `0x08` when wired (`k100.go:2730`, `CKB bragi_proto.h BRAGI_MAGIC 0x08`, `ORGB CorsairPeripheralV2Controller.h:27` `WRITE_WIRED_ID 8`).
- Through a dongle, target is `0x08 + deviceType` (`slipstream.go:801-812`). It is `0x09` when only one device is paired (`slipstream.go:810-812`; `ORGB ...h:28` `WRITE_WIRELESS_ID 9`). **[C]**

## 3. Init, software mode, hardware mode and timing

### 3.1 K100 RGB (wired), OLH order (`k100.go:269-294`, all **[V]**)

1. Read the HID manufacturer and serial strings (hidapi). The serial identifies the device.
2. `08 01 03 00 02`: SET mode = software (`k100.go:633-639`).
3. `08 0d 01 22`: open handle 1 on resource 0x22. Then **sleep 500 ms** (`k100.go:655-662`, `transferTimeout=500`).
4. `08 02 13`: firmware version.
5. Write the full LED frame (§4).
6. Brightness: `08 01 02 00 <u16 LE>` and `08 01 6d 00 <u16 LE>` (`k100.go:1908-1921`).
7. Start the IF2 listener.
8. Win-lock: `08 01 4a 00 <mask>` and `08 01 45 00 <0|1>`. Then write the key-assignment table (§6.1).
9. Debounce: `08 01 09 00 01`, `08 01 39 00 01`, then `08 01 0a 00 <30+ms>` and `08 01 38 00 <30+ms>` (`k100.go:1945-1982`).
10. **Keepalive** `08 12` every **20 s** (`k100.go:155,895-923`).

Timing comparison:

- ckb-next polls every **50 s** ("CUE polls devices every 52 seconds", `device_bragi.c:14-15`).
- OpenRGB's update period is 30 s (`ORGB ...Controller.h:34`).
- So an interval of 20-50 s is safe. **[C]**
- That the firmware falls back to HW mode without keepalives is **[I]**.

ckb-next's order (`device_bragi.c:149-200`, `setactive_bragi` at 38-125):

1. GET 0x03. If HW, SET it to SW.
2. GET 0x13, 0x14, 0x15, 0x16, 0x01, 0x96, 0x02 (or 0x44).
3. GET 0x41 (layout).
4. Open the lighting handle on res 0x01. If that returns 0x01 or 0x06, open res 0x22 and switch to interleaved output, then also open handle 2 on res 0x2e. **[V]**

### 3.2 Leaving software mode

OLH closes by sending `08 01 03 00 01` (HW mode) and then closing the device (`k100.go:332-365`). ckb-next closes the lighting handles first (`device_bragi.c:39-42`). OpenRGB's destructor also sets HW mode, because some boards stop generating onboard input events otherwise (`ORGB Controller.cpp` destructor comment). **[C]**

### 3.3 Software mode versus hardware mode

- **HW mode (1):** the firmware runs the active onboard profile, including lighting, remaps, wheel modes, G-key macros and the profile key. **[C]** (Corsair manual "HARDWARE MODE"; CKB)
- **SW mode (2):** the host streams lighting. Keys whose assignment byte is "default" still send HID on IF0. Every key is also reported as a bitfield on IF2. **[C]**

### 3.4 Polling-rate change

OLH tears down its workers, sleeps 40 ms and then sends SET 0x01 (`k100.go:1012-1040`). The device very likely re-enumerates afterwards, so the plugin must expect hidraw nodes to disappear and come back. **[I]**

## 4. K100 RGB lighting

### 4.1 Frame (resource 0x22)

```
08 06 <h> <len u32 LE> 12 00 R0 G0 B0 R1 G1 B1 ... R192 G192 B192
len = 2 + 3*193 = 581 (0x245)
```

- ckb-next sets `len = 3*zones + 2`, prefix `pkt[7]=0x12` (`CKB/src/daemon/led_bragi.c:128-160`) with zones = 193 (`led_bragi.c:44-46`).
- OLH uses `dataTypeSetColor {12 00}` and a 581-byte data array (`k100.go:144,162,2392-2425`). OLH writes `len=581` but sends 583 bytes; the extra 2 bytes are ignored.
- OpenRGB "Triplets" writes the `0x0012` LE prefix and RGB triplets (`ORGB/CorsairPeripheralV2HardwareController.cpp:66-84`).

**[C]** across all three.

With 1024-byte frames the whole update fits in one packet (3 + 4 + 583 < 1024). OLH splits with `maxBufferSizePerRequest = 1021` (`k100.go:161`). If 64-byte frames are used, continuations are `08 07 <h> + 61 bytes`.

- OLH's K100 continuation constant `{07 00}` (`k100.go:145`) names handle 0, while the K70 PRO uses `{07 01}`. That is a latent OLH bug which never triggers with jumbo frames. **[V]**
- OpenRGB paces continuation packets by 2 ms because the "K100 drops packets back to back" (`ORGB Controller.cpp:419-424`, `CORSAIR_V2_WRITE_PACE 2`). **[V]**

LED count: 193. ckb-next uses 193 (`led_bragi.c:44`); OLH's `LEDChannels: 194` (`k100.go:215`) is the buffer size rounded up. OLH has an off-by-one: it copies only 21 bytes to `data[546:567]`, so it never writes LED 189 from its wheel colour (`k100.go:2403`). **[V]**

Physical layouts: OLH ships K100 US/UK/DE/FR/SE JSONs (`database/keyboard/k100*.json`). ISO adds `bslash_iso` (100) and `hash` (50). **[C]**

### 4.3 Brightness

Brightness is hardware. SET 0x02 takes a u16 from 0 to 1000; OLH also writes 0x6d with the same value. ckb-next sets 0 to blank the board when every channel is 0, and 1000 to restore it (`led_bragi.c:105-111`). **[C]**

### 4.4 Wheel ring in software mode

In SW mode the host owns the ring. OLH paints all 8 wheel LEDs in the current "dial mode" colour (`k100.go:1482-1509`) and cycles modes itself when the wheel button is pressed (`k100.go:2869-2877`). **[V]**

### 4.5 Hardware lighting (firmware effects) on the wired K100 RGB

Not implemented in OLH for the K100 RGB; OLH only streams. **[V]** OpenRGB has a commented-out HW-mode writer (`ORGB Controller.cpp` UpdateHWMode) using the same effect record as §7.3. **[I]** that the K100 RGB accepts it.

### 4.6 Resource 0x2e "extra lighting" overlay

Frame: `08 06 <h> <len> 2b 00` followed by 5-byte entries `{led_id, c0, c1, c2, 0xff}`.

- ckb's commented K100 capture (`device_bragi.c:120-130`): len 0x48 = 72 bytes; LEDs 0x00, 0x01, 0x02, 0x72 (114 lock), 0x80 (128 profile), 0x89 (137 wheel button), 0xb6..0xbd (182..189 ring). These are exactly the firmware-owned indicator and ring LEDs.
- OLH's K100 AIR `controlTopBar` writes entries for 0x02, 0x01, 0x03, 0x72 (lock), 0x71 (brightness key), 0x80 (profile), 0x6c (Win) (`k100airW.go:609-645`), using data type `2b 00` (`k100airW.go:130`).

**[C]** format; colour byte order **[I]**. Useful for driving indicator LEDs without touching the main buffer. ckb notes it broke the '3' key on one firmware (0.32.6), so treat it as optional.

## 5. Input events (IF2), K100 RGB and K100 AIR wired

### 5.1 Key bitfield

- Layout: `[1]=0x02`, then `[2..21]` = 20 bytes = a 160-bit LE bitfield. Bit *n* = key index *n*, using the same indices as the LED table.
- OLH reverses the bytes and builds a big.Int whose value is 2^n (`k100.go:2825-2843`); see the `keyHash` values in k100.json (ESC = 2^41).
- ckb-next: `corsair_kbcopy(..., buffer+2)` (`keymap.c:908-912`).
- Includes: G1..G6 = bits 131..136, profile = 128, wheel button = 137, Win-lock = 114, media 123..126, mute 102, Fn 122.
- OLH masks byte 13 bits 0x04 (bit 106, lshift) and 0x40 (bit 110, rshift) before hashing (`k100.go:2831-2837`).

**[C]**

### 5.2 Control wheel

- Layout: `[1]=0x05`, `[2]=0x60`, `[4..7]` = signed i32 LE. +1 means clockwise (OLH: `[4]==0x01`); −1 means counter-clockwise (OLH: `[4]==0xFF`). Each event is one detent.
- There is no key-up; ckb-next synthesizes release events (`input.c:15`, `keymap.c:902-905`).
- Sources: OLH `k100.go:3173-3256`; CKB `keymap.c:914-924`, `bragi_proto.h BRAGI_INPUT_DIAL 0x05`. **[C]**
- The K65 PLUS rotary dial uses the same `[1]=0x05` event (`k65plusWU.go:2984`, `k65plusW.go:2441`, `k65plusWdongle.go:631`). **[C]**

### 5.3 Notifications

`[1]=0x01` is a notification, e.g. `[2]=0x36` connection/sub-device status from a dongle (`CKB keymap.c:826-828`; OLH `slipstream.go:1438`). **[C]**

### 5.4 Volume roller and media keys

These arrive as ordinary HID consumer events on IF0 (OLH `noColor` "WH +/-" with default action). Media usages 0xB5/B6/B7/CD/E2/E9/EA are listed at `CKB keymap.c:617-640`. **[C]**

## 6. Remapping, macros, profiles and G keys

### 6.1 Key-assignment table (resource 0x02)

K100 RGB sequence:

```
08 0d 02 02                     (open handle 2, resource 0x02)
08 06 02 <len u32> <138 bytes>
08 05 01 02                     (close)
```

- Byte *i* (key index *i*) is `0x01` for default HID behaviour or `0x00` to suppress firmware output so the host handles the key (`k100.go:150-152,164,395-425,3090-3114`). **[V]**
- K100 AIR wired: 135 bytes, chunked at 1021 (`k100airWU.go:163-164,390-437,2853-2885`). Per-key values come from the layout JSON `keyData = [index, default, intercepted]`:
  - normal keys: 0x39 default / 0x38 intercepted
  - modifiers and Fn: 0x3f / 0x3e

  This suggests bit 0 is the "send HID" flag and the high bits are the key class. **[V]** values, **[I]** meaning.
- K65 PLUS W: `0d 01 02` / `06 01` / `07 01` / `05 01 01`, 123 entries (`k65plusW.go:136-150`). **[V]**

### 6.2 G1..G6 macros

- In SW mode the plugin sees bits 131..136 on IF2. Set those entries to 0x00 in the assignment table so the firmware sends nothing, then run the macro in userspace (uinput). This is how OLH does all macros (`k100.go:2938-3060`). **[V]**
- Onboard (HW) macros are written by iCUE "Device Memory Mode"; the format is not public. **[I]**

### 6.3 Profile key

Bit 128. In HW mode the firmware cycles onboard profiles. In SW mode OLH rotates its own host profiles (`k100.go:960-998`, action type 22). **[C]**

### 6.4 Macro recording

The K100 RGB has **no dedicated MR key**; recording is one of the control-wheel modes (cycle to macro mode, hold the wheel button, press a G key, type, press the G key again). Sources: Corsair help article 360050055212; ckb `"mr"` has LED −1 (`keymap.c:456`). **[C]**

The K100 AIR uses the Profile key (hold 2 s) as its macro-record key, per the Corsair K100 AIR manual. **[V]** (web) The K65 PLUS uses FN+M (Corsair manual). **[V]**

### 6.5 Onboard profiles

- K100 RGB: 8 MB, "up to 200, depending on complexity" (Corsair product overview table). K100 AIR: 8 MB, up to 20 lighting layers per profile (manual). **[C]**
- How they are written: not documented in any open source. The evidence:
  1. ckb-next clears FEAT_HWLOAD for Bragi (`device_bragi.c:194`).
  2. OLH writes firmware lighting by opening a resource as a file (0x0013 index file, then 0x6d65 effect file), writing it, closing it and sending `0x15` commit, with `0x0b <res>` before (`k100airW.go:760-799,2570-2690`). Onboard profiles are very likely more such files.
- **[I]** Recommendation: do not implement. Treat the device as a host-driven SW-mode device and leave the onboard store untouched.

## 7. K100 AIR Wireless specifics

### 7.1 Wired (1bab)

Same as the K100 RGB except:

- 137 LEDs (0..136); data length 413 = 2 + 3·137 (`k100airWU.go:160,216`).
- Logo at LEDs 135-136 (`k100air.json` "LOGO").
- Brightness key LED 113 ("BTS"); G1..G4 at 131..134; no wheel and no lightbar (k100air.json dump).
- No 0x6d brightness and no debounce.
- Adds battery (0x0f/0x10), adaptive brightness (0xc4/0xc5), connection mode (0x3a).
- Polling up to 8000 Hz wired (`k100airWU.go:241-249`; RTINGS; Corsair manual "up to 8,000Hz hyper-polling").

**[C]**

- **Listener quirks:** modifiers are at event byte 15 (`modifierPosition: 15` in k100air.json) and Fn is `data[17]==0x04` (bit 122) (`k100airWU.go:3135-3146`). **[V]**

### 7.2 Through the SLIPSTREAM receiver (1ba6)

- 64-byte frames; target byte = sub-device endpoint (`k100airW.go:3175-3199`).
- Connect sequence (`k100airW.go:422-441`):
  1. heartbeat 0x12, retried 10×1 s
  2. SET mode = **6**
  3. battery
  4. firmware
  5. init LEDs
  6. effect
  7. brightness
  8. adaptive brightness
  9. sleep timer
  10. Win-lock

  **[V]**
- Init LEDs (`k100airW.go:760-799`): **[V]** sequence, **[I]** semantics.
  1. `0d 01 13 00` (open handle 1, res 0x0013)
  2. `09 01` probe
  3. write `69 6c 01 00 08 00 65 6d`
  4. close `05 01 01`
  5. `0b 65 6d`
  6. `0d 00 2e` (open handle 0, res 0x2e)
  7. sleep 500 ms
- Indicator overlay via `06 00 <len> 2b 00 …` (§4.6). **[V]**

### 7.3 Hardware-effect record (wireless)

OLH writes these with: open `0d 01 65 6d`, probe `09 01`, write `06 01`/`07 01`, close `05 01 01`, commit `15 01`. Generic layout, cross-checked with OpenRGB's commented HW writer:

```
u16 effect_id (LE) | u8 colour_mode (0 none, 1 specific, 2 random) | u8 speed (3 slow, 4 med, 5 fast) | u8 direction/extra
| ... | u8 n_colours | n × {0xFF, B, G, R} | u8 n_leds | n × led_id
```

Effect ids, as LE u16 with bytes as sent:

| Effect | Id | Bytes |
|---|---|---|
| Static | 0x207E | `7e 20` |
| Rain | 0xA07E | `7e a0` |
| Type-lighting key | 0xB1F9 | `f9 b1` |
| Type-lighting ripple | 0x09A2 | `a2 09` |
| Spiral rainbow | 0xAB87 | `87 ab` |
| Colour pulse | 0xAD4F | `4f ad` |
| Colour shift | 0xA5FA | `fa a5` |
| Colour wave | 0x7BFF | `ff 7b` |
| Rainbow wave | 0xB94C | `4c b9` |
| Visor | 0x90C0 | `c0 90` |
| Watercolour | 0x0022 | `22 00` |
| Gradient LUT (OLH only; 128 × {FF, B, G, R}) | 0xEBF4 | `f4 eb` |

Sources: OLH `k100airW.go:1786-2563`; ORGB `CorsairPeripheralV2Controller.h:64-77` enum. **[C]**

The Corsair manual's FN+1..0 onboard effects list matches this set exactly. **[C]**

- "Static/keyboard" sends one colour plus the LED id list (`k100airW.go:1821-1851`). OLH does **not** stream per-key frames over the dongle. **[V]**
- Whether resource 0x22 per-key streaming works over SLIPSTREAM is unknown. A ckb-next user reports the "wireless keymap is wrong" (issue #1022). **[I]**
- Other settings: sleep `01 0d 00 01` then `01 0e 00 <u32 ms>` (`k100airW.go:1021-1043`); battery `02 0f` (÷10 %) and `02 10`; BT switch `01 3a 00 02`; USB switch `02 3a 00 00` then `01 3a 00 00`. **[V]**

## 10. Implementation notes for the Rust plugin

1. **Discovery without opening devices.** Walk `/sys/class/hidraw/*/device`:
   - match `HID_ID` VID 1b1c and PID in {1b7c, 1b7d, 1bc5, 1bab, 1ba6, 2b07, 2b10, 2b11, 2b23}
   - get the interface number from the parent USB interface's `bInterfaceNumber`
   - read `report_descriptor` and parse page 0xFF42 Output report size (64 or 1024)
2. **One worker per device** owning IF1 (request/response, serialised; responses must be matched by `[1]` echo) and IF2 (blocking read loop for events).
3. **K100 RGB direct frame:** `[00, 08, 06, h, 0x45, 0x02, 0, 0, 0x12, 0x00, RGB×193]`, padded to the report size. Open the handle once at init (`08 0d h 22 00`). After errors, reopen it; status 0x03 means the handle is busy, so close it and retry.
4. **Pace writes** about 2 ms when chunking at 64 B. With 1024 B frames a full K100 frame is one write.
5. **On exit**, close the handles and set HW mode (`08 01 03 00 01`) so onboard features, the wheel and G-keys return to firmware control.
6. **Do not use** the 0x0b/0x15 file operations on wired boards. They touch onboard storage.
